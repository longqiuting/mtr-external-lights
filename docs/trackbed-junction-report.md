# 道床：弯道接直道后直道无碰撞（候选集 + 接缝 + where 诊断）

> 真机反馈（1.0.66 / 横向列 + 弧长插值那版）：*轨道如果是纯弯道没问题，但如果是弯道后立马衔接直道就出问题，直道部分完全没有碰撞箱。*

## 1. 取证：先把「几何」判死

取证不是读代码猜，而是**拿 MTR 3.6.4.2 的真实 `Rail` 对象跑**（`libs/MTR-fabric-1.20.1-3.6.4.2-named.jar` +
loom 的 named MC jar，反射读私有字段、直接调 `getPosition` / `getLength`）。

### 1.1 MTR 的轨道数据长什么样（实测，不是推断）

- 一条 `Rail` 由**两段**组成：`len1 = |tEnd1-tStart1|`、`len2 = |tEnd2-tStart2|`，
  `getLength() = len1+len2`，`getPosition(t)` 在 `t <= len1` 时取 segment1、否则取 segment2。
  **segment1 的切向 = 起点朝向、segment2 的切向 = 终点朝向**。
- 弯道：`x = h + r·cos(t/r) + 0.5`、`z = k + r·sin(t/r) + 0.5`（`t` 就是**弧长**）。
- 直道：`x = h·t + k·r + 0.5`、`z = k·t + h·r + 0.5`（`(h,k)` 是单位方向，`r` 是垂轴原点）。
- `(0,10) 朝 N → (5,5) 朝 E` 实测 `len = 7.853981633974485`、`p(0)=(0.5,10.5)`、`p(L)=(5.5,5.5)`；
  `(0,10) 朝 N → (15,5) 朝 E` 实测 `len1 = 7.8539816`（弧）+ `len2 = 10.0`（直线），接缝 `seamGap = 0`。

所以「弯道接直道」在数据里只有两种形态，**两种都测了**：
① 两条 `Rail`（相邻节点一段一条）；② 同一条 `Rail` 的两段（弧 + 直线）。

### 1.2 四种「嫌疑」逐个判死

| 嫌疑 | 结论 | 证据 |
|---|---|---|
| 弯道末采样点与直道入口的 y/位置不连续 | **不成立** | 两段接缝 `seamGap = 0`（1154 条两段式 Rail 全为 0），`getPosition` 在 `t = len1` 两侧连续 |
| 只按 `dist` 取最小 ⇒ 永远选弯道 | **不成立** | 站在直道上时直道的 `dist = 0`，弯道末端 `dist` 随距离单调增大，最小的一定是直道 |
| 折线包围盒外扩 `halfW+0.25` 算小 | **不成立** | 包围盒距离是**折线真实距离的下界**；`bboxDist > 1.55 ⇒ 真实距离 > 1.55`，而命中要求 `≤ 1.3`。**旧代码不可能丢掉一条能命中的轨道** |
| 候选集漏掉直道那条 | 这是**现象的唯一成因**，但触发点在「进缓存」而不是「包围盒」 | 见 §1.3、§1.4 |

模糊测试：`A(0,0) 朝向 f1 → B(bx,bz) 朝向 f2 → C` 扫 **4,242 个接缝场景**（16 种朝向 × 节点网格 ×
两段轨道），用旧版候选集逐点走中心线 —— **0 漏判**。另外扫 **24,336 条** MTR 构造结果，
`getPosition` 出 NaN 的 **0 条**。

### 1.3 那么「直道不在候选里」只能从三条**静默**路径发生

命中要求 `真实距离 ≤ 1.3`，而旧 `probe()` 的第二道包围盒判定是 `bboxDist ≤ 1.55`（下界判定，
只会多收不会漏收），所以**能命中却被候选集过滤，数学上不可能**。能让整条轨道消失的只有：

1. `build()` 的 `catch (Throwable)` 包在**整张表的循环外层** —— 任意一条轨道抛一次，**其后所有候选
   一起消失**，且 HashMap 迭代顺序稳定 ⇒ 同一条轨道每次都在同一处被截断（现象是「这个位置永远
   只剩弯道那条」）。`entry()` 对采样失败/NaN 更是**静默返回 null**，连 `warnOnce` 都打不到。
2. `physical()` 把 `railType` 判成 `NONE` / `AIRPLANE_DUMMY`（数据占位）——静默跳过。
3. 高度粗筛 `y < minY-4 || y > maxY+4` ——静默跳过。

这三条在 1.0.66 里**一条日志都不留**，所以「弯道在候选里、紧接着的直道不在」可以完全无声地发生。
`where` 诊断就是为这三条准备的：`cand=` 与 `skipped=` 一眼分开「表里没有」和「没进候选」。

### 1.4 现象会被放大成「整段没有碰撞箱」

`RailBed.verdict` 的下界是 `dy ≥ -stepUp(-1.0)`：**一旦哪一 tick 漏了、人掉到轨面 1 格以下，
之后每 tick 都是 `dy` → 再也不抬回来**。所以接缝处一次极小的判定抖动（横向超半宽 1 格、或候选少了
一条）在画面上就是「直道整段没有碰撞箱」。这条不用改模型（改 `dy` 下界会把跳跃吃掉），但解释了
为什么症状是「整段」而不是「一格」。

## 2. 修什么

### 2.1 候选集：按「查询点到折线的真实距离」构造（`RailBed.build` / `candidate`）

```
第一级  端点包围盒 + len/2 + reach   （三角不等式的保守粗筛，省掉远处 getPosition）
第二级  折线包围盒距离 ≤ reach       （真实距离的**精确下界**，剪枝不漏）
第三级  逐段投影出来的真实距离 ≤ CANDIDATE_REACH = halfW + 1.2 = 2.5
```

- 准入从「查询点是否落在包围盒（±1.55）里」换成**真实距离 ≤ 2.5**：贴着框外、接缝两侧的那小段
  轨道照样进候选。
- `build()` 的 `try/catch` 挪到**循环内部**：单条轨道失败只丢它自己，`skipped++` 计数进诊断。
- 采样出现 NaN/Inf **显式拒绝**（并计入 `skipped`），不再让 NaN 包围盒把一条轨道静默毒死
  （NaN 参与比较恒为假 ⇒ `within()` 永远 false ⇒ 那条轨道永远进不了候选，且没有任何日志）。
- 候选按「到锚点的真实距离」升序排列：接缝处两条谁更近，`where` 里直接看得出来。

### 2.2 接缝选边（`RailBed.probe`）

两条相邻轨道都在候选里，取 `dist` 最小；**并列（差 ≤ `SEAM_TIE` = 2cm）时优先「投影落在轨道内部」
的那条**。否则接缝处会残留一个偏置：弯道末端的投影被 clamp 在折线端点（`f = 1`）上，它的读数
按弯道末端的法向算，跟直道差半个弧度，`y` 也跟着用错的那条弧长插值。

### 2.3 新诊断 `/mtr_lte trackbed where`

站在出问题的位置跑一次，打表头 + 每条候选一行（最多 8 条，按距离从近到远）：

```
[lte] where at=(10.50, 64.00, 5.50) anchor=(10.00, 4.00) rails=2 near=2 cand=2 skipped=0 halfW=1.30 reach=2.50 hit=yes
[lte] where #1 dist=0.00 off=+0.00 y=64.00 along=5.00/10.00 straight=yes anchorDist=1.50 WOODEN WIN
[lte] where #2 dist=5.00 off=+0.06 y=64.00 along=7.85/7.85 straight=no  anchorDist=4.74 WOODEN (超出 halfW)
```

（这段是拿**仓库里真正的 RailBed** 在真实 MTR `Rail` 上跑出来的原样输出。）

读法：

| 看到什么 | 含义 |
|---|---|
| `cand=0` | 这个位置周围一条轨道都没进候选（轨道表没加载 / 人不在轨道上） |
| 表里**没有 `straight=yes` 那行** | 直道那条连候选都不是 —— 就是本次修的那类 |
| 有直道那行但 `dist > 1.30` | 轨道找到了、人横向没踩上（`off` 会给方向和数值） |
| `along` 贴着 `0.00` 或 `len` | 这条已经走到头，该选接缝对面那条 |
| `skipped≠0` | 表里有单条坏轨道被跳过（旧实现会被它**截断整张候选表**） |
| `hit=yes` 但仍然掉 | 不是几何问题：看 `status` 的 `drop=block|space`（`realBlockWins` / `isSpaceEmpty`） |

`status` 行同时加了 `scanned=` / `skipped=`。

## 3. 接缝仿真（`tools/trackbed-junction-sim.js`）

R=5 的 90° 弯道 + 10 格直道，几何按 §1.1 的 MTR 实测值铺；沿路径**每 0.1 格**采样，跑 RailBed 的
候选集算法（新旧两版都在脚本里）。

```
A. 弯道末点与直道起点重合（接缝位置连续）      gap=8.9e-16
A. 弯道末切向与直道切向一致（接缝相切）        T=(1.0000, -0.0000)
B. 中心线 179 个采样点全部命中（0 漏判）       miss=0
B. 同一条 Rail 两段（len1=弧 7.854 / len2=直线 10）  miss=0/179
C. 贴着道床 ±1.20 / ±1.28 并行走过接缝          miss=0 switches=1 worstY=0 worstOff=0.0005
C. 沿路径轨面 y 连续                            worstJump=0
D. 接缝 ±1 格内 curve 与 straight 同时在候选集里
E. 对照：候选里只剩弯道那条 ⇒ 直道段 101 点里漏 87，接缝 1.5 格以外 85/85 全漏
     离接缝 3 格处到弯道折线的距离 = 3.00 > halfW 1.30 → 掉
```

E 段是这次的关键取证：**「直道不在候选集」这一条本身，就足以 100% 复现用户看到的现象**；而 A/B/C/D
说明候选集齐的时候接缝没有任何空洞（>2cm 的空洞 0 个）。

用法：`node tools/trackbed-junction-sim.js`（`--all` 打全部 0.1 格采样行）。

## 4. 现场下一步

1. 站到出问题的直道上，`/mtr_lte trackbed where`；
2. 若表里没有 `straight=yes` 那行 → 直道压根没进候选，看 `skipped=` 与 `rails=`（判断是数据面还是被截断）；
3. 若有那行但 `dist > halfW` → 横向问题，`off` 的符号告诉你是哪一侧；
4. 若 `hit=yes` 仍掉 → `/mtr_lte trackbed status` 看 `drop=`，`block`/`space` 说明是真实方块或落点空间
   不足（`realBlockWins` / `isSpaceEmpty`），不是几何。

## 5. 状态延续（第五轮：不再每 tick 从零查表）

前四轮都在「让查表更准」上加条件（真实距离准入、接缝选边、三级判据、下落安全网），但真机上
**弯道接直的直道段照样掉**。这一轮换掉模型本身：**不再每 tick 从零查表**，而是记住上一 tick
踩着的那条轨道。

### 5.1 三级判定顺序（`RailBed.follow`）

| 级别 | 条件 | 查表？ |
|---|---|---|
| 1 `cont` 延续 | 上一 tick 的轨道 + 弧长 `s`，按本 tick 位移把窗口推到 `s ± (位移+0.6)`，只在**这一段**的折线上做局部投影 | **不查** |
| 2 `table` 回退 | 延续不成（走到这条的头了 / 离折线 > 1.6）才走原来的候选集查询 | 查 |
| 3 `hop` 跨段 | 查表也没命中，但人在上一段**末端 2.5 格**内、且已在行进方向上越过端点 → 端点键直接取下一条 | 只有一次 Map 查 |

接受条件三级共用：横向（到折线真实距离）≤ `FOLLOW_REACH` 1.6、脚底 − 轨面 ∈
[−1.5, +1.0]；**投影被钳在端点且已走出半宽** 视为「这条走到头了」，交给下一级。

命中之后 `lastRail/s/y` 换成新的，所以过了接缝的每一 tick 都在延续链上。

### 5.2 跨段用的数据结构

MTR 的轨道表 `Map<BlockPos, Map<BlockPos, Rail>>` 是**双向**的（两个端点都是键：`rails.get(A)`
里同时有 `A→B` 和反向伙伴 `A→Z`，见 ANTE 的 `BrushEditRailScreen` 与 `BlockDirectNode` 的用法）。
所以跨段不需要扫表、也不需要候选缓存：

```
rails.get(当前轨道末端键) → Map<另一端点键, Rail>
  ├─ 跳过 rail == 当前轨（同一个对象）
  ├─ 跳过 另一端点 == 当前轨起点（原路返回的反向伙伴，否则原地来回跳）
  ├─ 切向点积 > 0.25（夹角 < 75°，岔道里方向不对的那条会让下一 tick 倒着走）
  └─ 剩下按「到折线真实距离」取最近
```

### 5.3 现场读法：每 5 秒一行的 `follow` 汇总（不依赖任何开关）

```
[lte] trackbed follow: rail=yes seg=arc/7.85 s=3.20 y=64.00 ok=380 lost=0 hop=2 table=1
```

`lost` 不为 0 才是**真掉**（上一 tick 还踩着、这一 tick 三级全断）。`hop` 是跨段次数，
过接缝时它应该 +1；`table` 是回退查表的次数（不该每 tick 都在涨）。

### 5.4 仿真（`tools/trackbed-follow-sim.js`）

R=5 弧 → 10 格直道 → R=5 弧，3 段轨道 + 反向伙伴，表的**候选缓存故意看不到直道那条**
（§1.3 的静默路径），玩家以 0.215 格/tick 走过全程，3 个起点 × 3 种横向偏移 + 反向一遍：

```
lookup-only（每 tick 从零查表）  直道段 34–40 个 tick 全丢   ← 复现用户报的现象
follow（延续 → 查表 → 跨段）     lost=0，cont≈全程，hop=1（过接缝时）
RESULT lost=0
```

用法：`node tools/trackbed-follow-sim.js`（`--all` 打逐 tick 的段落/距离）。
